# 머지 전 검증

검증 대상: $ARGUMENTS

- 인자가 비어 있으면 `git diff upstream/main...HEAD` 를 검증 대상으로 삼는다.
- 인자가 git 범위(예: `main...HEAD`, 커밋 해시)이면 그 범위의 diff를 대상으로 한다.
- 인자가 patch 파일(예: `vendor-prs/*.patch`)이면 그 patch 내용을 대상으로 한다. patch 파일 자체는 수정하지 않는다.

판정 기준과 체크리스트 항목은 저장소 루트의 `templates/approval-checklist.md` 를, 절차의 근거는 저장소 루트의 `templates/verification-loop.md` 를 따른다. 체크리스트 항목은 이 문서에 옮겨 적지 않고 매번 그 파일을 읽어 대조한다.

## 원칙

- 이 Skill은 리뷰 세션의 역할만 한다. 코드를 수정하지 않는다. 고치기 시작하면 검증하는 쪽이 아니라 만든 쪽이 된다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.

## 절차

### 1. 요청 범위 확인

- 이 변경이 무엇을 요청받아 만든 것인지 한 문장으로 확인한다.
- 요청 범위가 주어지지 않았으면 판정하지 말고 먼저 사용자에게 질문한다. 범위를 모르는 상태에서 다음 단계로 넘어가지 않는다.

### 2. 변경 파일 목록과 diff 읽기

- git 범위이면 `git diff --stat <범위>` 로 변경 파일 목록을 먼저 보고, 파일마다 `git diff <범위> -- <파일>` 로 diff를 읽는다.
- patch 파일이면 `git apply --stat <patch>` 로 변경 파일 목록을 뽑은 뒤 patch 본문을 파일 단위로 읽는다.
- 판정에 필요하면 변경된 파일 전체를 읽는다.

### 3. 체크리스트 대조

직접 대조하지 않고 reviewer Sub-agent에 위임한다.

- 1단계에서 확인한 요청 범위와 검증 대상(비교 범위)을 그대로 넘긴다.
- reviewer는 `templates/approval-checklist.md` 를 읽고 항목마다 충족 · 미충족 · 확인 필요로 표시하며, 심각도 정의(치명 / 경고 / 제안)에 따라 이슈를 분류해 보고한다.

### 4. 테스트 실행

직접 실행하지 않고 tester Sub-agent에 위임한다. 변경된 폴더의 테스트만 실행하며, 명령은 저장소 루트에서 실행한다.

- 새 로직에 테스트가 없으면 tester가 테스트 파일을 추가한 뒤 실행하고, 추가한 파일 목록과 실행 결과를 돌려받는다.

| 변경된 폴더 | 실행 명령 |
|---|---|
| `modern/api` | `(cd modern/api && ./gradlew test)` |
| `modern/web` | `(cd modern/web && npm test)` |
| 이관 코드(레거시 기능을 `modern/` 으로 옮긴 변경) | `(cd characterization && npm test)` — 레거시 대상<br>`(cd characterization && TARGET_BASE_URL=http://localhost:8080 npm test)` — 새 API 대상 |

- characterization 테스트는 레거시 서버와 새 API(`modern/api`, 8080 포트)가 떠 있어야 한다. 서버가 꺼져 있거나 의존성이 설치되지 않아 실행할 수 없으면 그 사실을 결과에 적고 사용자에게 기동을 요청한다. 이 경우 "테스트 통과" 기준은 충족으로 표시하지 않는다.
- 사용량 절약: 테스트 출력 전체를 대화에 싣지 않는다. 명령마다 통과 수 · 실패 수와 실패한 테스트 이름만 남긴다. 필요하면 출력을 파일로 받아 요약 줄과 실패 이름만 추려 읽는다.

### 5. 승인 기준 판정

- reviewer와 tester의 두 보고를 받은 뒤, 메인 세션이 아래 기준을 모두 최종 판정한다.
- 두 보고가 엇갈리면 엇갈린 지점을 그대로 적고 사람에게 묻는다. 임의로 한쪽을 택하지 않는다.
- 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다.
- 네 기준이 모두 충족되어야 승인이다. 하나라도 미충족이면 반려한다.
- 이슈가 0건이면 경고 · 제안 수준까지 한 번 더 확인한다. 0건은 결과일 수도, 보지 않은 것일 수도 있다.

reviewer 또는 tester Sub-agent가 없는 환경에서는 3단계와 4단계를 기존 방식대로 직접 수행한다.

## 출력 형식

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
| 1 | 치명 / 경고 / 제안 | path/to/File.java:42 | ... | ... |

확인 필요
- 근거 줄번호를 댈 수 없었던 지적
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 순서로 네 항목을 모두 채운다.

## 하지 말 것

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 보고만 한다.
- 근거 줄번호를 댈 수 없는 지적은 하지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.
- 요청 범위를 모르는 상태에서 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.
- 테스트 전체 로그를 대화에 싣지 않는다.
- 체크리스트 항목을 이 문서에 복사하지 않는다. 저장소 루트의 `templates/approval-checklist.md` 를 참조한다.
